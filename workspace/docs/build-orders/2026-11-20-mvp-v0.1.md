# BUILD ORDER — LYKOS REIMARCHIV MVP v0.1

> Status: umgesetzt am 2026-11-20. Bereiche A01–A07 wurden mit `2026-11-20-ui-reduction.md` auf vier Navigationsziele reduziert.

## 1. Auftrag

Baue das erste lokal ausführbare MVP des Projekts LYKOS REIMARCHIV für Windows.

Ziel ist zunächst ein vollständiges, visuell ausgearbeitetes Desktop-Frontend, dessen einzelne Bereiche wir anschließend gezielt und schrittweise gemeinsam entwickeln.

Die Anwendung muss lokal startbar sein und eine Desktop-Verknüpfung erhalten.

## 2. Vor Arbeitsbeginn

1. Repository und vorhandene Projektdateien untersuchen.
2. `start-draft.md` vollständig lesen.
3. Bereits getroffene Projektentscheidungen übernehmen.
4. Keine bestehenden Entscheidungen ohne Rücksprache verändern.
5. Vorhandene Dateien nicht unnötig neu strukturieren.

Bei fehlenden technischen Entscheidungen eine einfache, passende Lösung wählen und dokumentieren.

## 3. Technischer Rahmen

- Zielplattform: Windows 10/11
- Backend: Go
- Desktop-Anwendung: eigenständig ausführbare Anwendung
- Datenhaltung: SQLite vorbereiten, noch keine umfangreiche Datenlogik implementieren.
- Frontend: moderne, übersichtliche Desktop-Oberfläche.
- Keine Cloud-Abhängigkeit.
- Keine kostenpflichtigen Dienste.
- Keine unnötigen Frameworks oder Abstraktionen.

Die konkrete GUI-Technologie anhand des vorhandenen Projekts und der Anforderungen auswählen.

## 4. Frontend – Hauptbereiche

Erstelle eine vollständige Navigation mit folgenden Bereichen:

### A01 — Dashboard
- Übersicht der Anwendung
- Schnellzugriffe
- Entwicklungsstatus der Module
- Platzhalter für Statistiken

### A02 — Reimarchiv
- Reimwort-Verwaltung
- Vokalkategorien A, E, I, O, U
- Einsilbige Wörter
- Reimlisten
- Suchfeld
- Platzhalter für phonetische Reimanalyse

### A03 — Relatable-Sätze
- Satzarchiv
- Satzsammlungen
- Themenkategorien
- Favoriten
- Platzhalter für Satzgenerierung

### A04 — Generator
- Eingabefeld für Endwort
- Reimkategorie
- Silbenbegrenzung
- Kontrastoptionen
- Generierungsbereich
- Platzhalter für die eigentliche Generierungslogik

### A05 — Analyse
- Silbenanalyse
- Phonetische Reimanalyse
- Reimqualität
- Betonungsmuster
- Platzhalter für Analysefunktionen

### A06 — Sammlungen
- Eigene Sammlungen
- Gespeicherte Reimketten
- Favoriten
- Platzhalter für Songprojekte

### A07 — Einstellungen
- Anwendungsinformationen
- Datenbankstatus
- Export und Import
- Backup
- Oberflächeneinstellungen

## 5. Entwicklungszustände sichtbar machen

Jeder Bereich und jede Funktion muss einen klar erkennbaren Entwicklungsstatus besitzen:

- IMPLEMENTIERT
- IN ENTWICKLUNG
- PLATZHALTER
- GEPLANT

Nicht implementierte Funktionen dürfen nicht so dargestellt werden, als würden sie bereits funktionieren.

Platzhalter sollen bereits die vorgesehenen Bedienelemente, Beschriftungen und Layouts enthalten.

Jeder Bereich soll visuell und strukturell eigenständig weiterentwickelbar sein.

## 6. Design

Orientiere dich an einem minimalistischen, dunklen Desktop-Interface:

- Anthrazit / Schwarz als Grundfarben
- Neon-Grün als Akzentfarbe
- Klare Typografie
- Permanente linke Navigation
- Übersichtlich strukturierte Inhaltsbereiche
- Dezente Rahmen und Karten
- Keine überladenen Dashboards
- Keine unnötigen Animationen

Die Anwendung soll wie ein professionelles eigenständiges Songwriting-Werkzeug wirken.

## 7. Technische Anforderungen

- Saubere Projektstruktur
- Klare Trennung zwischen UI und Anwendungslogik
- Einheitliche Navigation
- Wiederverwendbare UI-Komponenten
- Lokale Startfähigkeit
- Fehlerfreie Kompilierung
- Keine externen Server als Startvoraussetzung

## 8. Build und Desktop-Verknüpfung

Am Ende muss Folgendes vorhanden sein:

1. Kompilierte Windows-EXE.
2. Funktionierende Desktop-Anwendung.
3. Automatisch erstellbare Windows-Desktop-Verknüpfung.
4. Startskript für die lokale Entwicklung.
5. Build-Skript für die erneute Erstellung der EXE.
6. README mit den notwendigen Start- und Build-Befehlen.

Die Verknüpfung muss auf die tatsächlich kompilierte Anwendung zeigen.

## 9. Explizite Grenzen

NICHT implementieren:

- Keine vollständige Reimengine.
- Keine KI-Anbindung.
- Keine automatische Satzgenerierung.
- Keine komplexe semantische Suche.
- Keine umfangreiche Grammatikprüfung.
- Keine vorgetäuschte Funktionalität.

Die phonetische Architektur und die beschlossene Reim-Roadmap aus `start-draft.md` bleiben als Grundlage erhalten.

## 10. Abschlusskriterien

Der Auftrag ist erst abgeschlossen, wenn:

- Die Anwendung lokal startet.
- Die Navigation funktioniert.
- Alle sieben Hauptbereiche erreichbar sind.
- Platzhalter eindeutig gekennzeichnet sind.
- Das Design konsistent ist.
- Die EXE erfolgreich erstellt wurde.
- Eine Desktop-Verknüpfung funktioniert.
- Die Anwendung ohne Internetverbindung startet.

## Arbeitsprinzip

Baue zuerst ein funktionierendes, vollständiges Frontend-Grundgerüst.

Keine unnötige Architektur, keine vorschnelle Implementierung zukünftiger Funktionen und keine zusätzlichen Module ohne konkreten Bedarf.

Das Ergebnis ist die gemeinsame Arbeitsoberfläche für die anschließende schrittweise Entwicklung des LYKOS REIMARCHIV.
